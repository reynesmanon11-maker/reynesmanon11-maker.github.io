01 Ce qu'est Claude Code

Le point de départ, à dire en une phrase.

Claude Code, c'est Claude qui a accès à un dossier de fichiers. La différence avec le chat classique tient en cela : au lieu de vous répondre du texte que vous copiez-collez ensuite, Claude ouvre les fichiers, les modifie, en crée de nouveaux, lance des commandes, enregistre le travail dans l'historique du projet (Git) et le met en ligne.

Le chat classique

Vous demandez du code → Claude affiche du code → vous le copiez dans votre éditeur → vous l'enregistrez → vous l'envoyez sur GitHub. Cinq étapes manuelles.

Claude Code

Vous demandez une page → Claude crée le fichier, l'écrit, le teste, l'enregistre et le publie. Vous relisez le résultat en ligne. Une étape.

Concrètement, dans ce projet, une phrase comme « ajoute une activité interactive sur le cycle des roches pour les 2ndes » a produit le fichier cycle_des_roches_2nde.html, son enregistrement dans l'historique et sa mise en ligne — sans qu'aucune ligne de code ne soit copiée à la main.

La même chose, quatre façons d'y accéder. On choisit selon le confort, pas selon la puissance.

Particularité du mode navigateur

La machine distante est éphémère : elle disparaît après la session. Tout ce qui n'a pas été enregistré et envoyé sur GitHub est perdu. D'où l'importance de la partie Git (§ 5) : ce n'est pas une formalité de développeur, c'est le seul endroit où le travail survit.

03 Sa première session, pas à pas

À faire en direct devant la personne formée.

  1. Aller sur claude.ai/code et se connecter.
  2. Choisir le dépôt GitHub sur lequel travailler (ici reynesmanon11-maker.github.io). Un dépôt = un dossier de projet hébergé chez GitHub.
  3. Choisir l'environnement : c'est la machine distante et sa configuration (variables, accès réseau, script de démarrage). Le réglage par défaut suffit pour du HTML.
  4. Écrire sa demande en français, normalement, comme à un collègue.
  5. Regarder Claude travailler : il annonce ce qu'il lit, ce qu'il modifie, ce qu'il lance. On peut l'interrompre à tout moment pour corriger la trajectoire.
  6. Relire le résultat, demander les ajustements, puis lui demander d'enregistrer et de publier.

Le réflexe à installer dès la première minute

On ne valide pas au premier jet. On regarde la page, on dit ce qui ne va pas (« le texte du bouton est illisible », « il manque la correction de l'exercice 3 »), et on relance. Trois allers-retours valent mieux qu'une demande initiale de vingt lignes.

04 Bien formuler sa demande

C'est 80 % du résultat. Rien de technique là-dedans.

Une bonne demande répond à quatre questions : quoi, pour qui, où, avec quelles contraintes.

Demande trop vague

« Fais-moi une page sur les roches. »

Claude devine le niveau, le format, le style — et se trompe une fois sur deux.

Demande exploitable

« Crée une page HTML autonome pour des élèves de 2nde sur le cycle des roches : un schéma cliquable, trois définitions, un quiz de 5 questions avec correction immédiate. Même charte graphique que index.html. Fichier cycle_des_roches_2nde.html. »

Trois formulations qui font gagner du temps

  • « Comme dans tel fichier » — Claude lit le fichier cité et en reprend la charte, la structure, le ton.
  • « Explique-moi d'abord ce que tu comptes faire, ne code pas encore » — utile pour les gros chantiers ; on valide le plan avant l'exécution.
  • « Ne touche à rien d'autre » — délimite le périmètre quand on veut une retouche chirurgicale.

Fichiers joints

On peut déposer une photo, un PDF, une capture d'écran. Dans ce projet, une photo de restaurant (le-vieux-logis-restaurant.jpg) et des visuels (terre.png, terre.jpg) ont servi de matière première à des pages. Une capture d'écran d'un affichage raté est souvent la façon la plus rapide de signaler un bug.

05 Git : branches et commits, expliqués sans jargon

La notion la plus rentable de tout le tutoriel.

Git est le carnet de bord du projet. Trois mots suffisent :

MotTraductionDans la vraie vie
commitUn point de sauvegarde daté et commenté Correction IA v7 : grille manuelle, remédiation ciblée…
brancheUn brouillon parallèle, isolé de la version en ligne claude/claude-code-tutorial-879tki
pushEnvoyer les sauvegardes sur GitHub Le moment où le travail devient durable

Claude Code travaille systématiquement sur une branche dédiée, jamais directement sur main (la version publiée). C'est ce qui rend l'outil sans danger : tant que la branche n'est pas fusionnée, le site en ligne n'a pas bougé d'un pixel. Les noms de branche commencent par claude/, suivis du sujet et d'un identifiant aléatoire.

$ git log --oneline
6bc4bd8  V9 : barèmes ultra-détaillés, cache API, bouton Valider ma grille
589aa7a  Merge pull request #1 from .../claude/genially-autonomous-creation-sjdu7d
800383c  Ajout d'une activité interactive : le cycle des roches (2nde SVT)
96f122b  Correction IA v8 : synchronisation cloud hybride optionnelle

Cet historique se lit comme un journal de bord : chaque ligne dit ce qui a changé et pourquoi. On peut revenir à n'importe lequel de ces points — rien n'est jamais définitivement cassé. C'est l'argument à donner en priorité à quelqu'un qui a peur de « tout casser ».

Phrases à dire à Claude

  • « Enregistre le travail avec un message clair et pousse la branche. »
  • « Montre-moi ce que tu as changé avant d'enregistrer. »
  • « Reviens à la version d'avant, cette modification ne me convient pas. »

06 Pull request : relire avant de publier

L'étape qui transforme un brouillon en version officielle.

Une pull request (PR) est une demande de fusion : « voici ce que ma branche change par rapport au site en ligne, est-ce qu'on l'accepte ? ». GitHub affiche alors le diff : les lignes ajoutées en vert, supprimées en rouge.

  1. Claude pousse la branche puis ouvre la PR — uniquement si on le lui demande.
  2. On relit le diff sur GitHub, ou plus simplement on regarde la page rendue.
  3. On demande des corrections : Claude ajoute des commits sur la même branche, la PR se met à jour toute seule.
  4. On clique sur Merge : les changements rejoignent main, le site se met à jour.

C'est ce qui s'est passé avec la PR #1 de ce dépôt : l'activité sur le cycle des roches a été préparée sur une branche, relue, puis fusionnée dans main.

Bonus : Claude peut surveiller sa propre PR

On peut lui demander de suivre une pull request : il reçoit les commentaires de relecture et les résultats des tests automatiques, et corrige tout seul jusqu'à ce que tout soit au vert.

07 Publier avec GitHub Pages

Pourquoi ce dépôt porte un nom aussi bizarre.

Un dépôt nommé identifiant.github.io est automatiquement publié par GitHub à l'adresse https://identifiant.github.io. Hébergement gratuit, HTTPS inclus, aucune configuration.

Fichier dans le dépôtAdresse publique
index.htmlreynesmanon11-maker.github.io
cycle_des_roches_2nde.html…github.io/cycle_des_roches_2nde.html
correction_copies.html…github.io/correction_copies.html

D'où le choix technique fait sur tout ce projet : une activité = un seul fichier HTML autonome, qui embarque son style et ses scripts. Pas de serveur, pas d'installation, pas de dépendance qui casse dans six mois. Le lien se colle dans l'ENT, il fonctionne sur le téléphone des élèves.

Délai de mise en ligne

Comptez une à deux minutes entre la fusion et l'affichage réel. Si la page semble inchangée, c'est presque toujours le cache du navigateur : Ctrl+F5.

08 Itérer : l'histoire de l'outil de correction

Le meilleur exemple pédagogique du dépôt — neuf versions en quatre jours.

L'outil correction_copies.html n'a pas été obtenu d'un coup. Il s'est construit par ajustements successifs, chacun venant d'un usage réel :

VersionProblème constatéRéponse
v1—Première ébauche : coller une copie, obtenir une note
v3Notes trop binairesGrilles à niveaux, observations, copie imprimable
v4Interface confuseRefonte claire, trois zones, export PDF
v5Deux corrections de la même copie donnaient deux notesNotation reproductible, total du barème préservé
v6Même exigence en 2nde et en TerminaleExigence adaptée au niveau, PDF fiabilisé
v7Surnotation systématiqueCalibrage anti-surnotation, remédiation ciblée par type d'erreur
v8Travail perdu en changeant d'ordinateurSynchronisation cloud optionnelle
v9Barème appliqué approximativement, coût des appelsBarèmes ultra-détaillés, cache des appels API, bouton « Valider ma grille »

La leçon à transmettre

On ne rédige pas le cahier des charges parfait au départ. On sort une v1 utilisable, on s'en sert pour de vrai, et chaque agacement devient la demande suivante. Chaque version est un commit : si la v7 était moins bonne que la v6, on revenait en arrière en une phrase.

09 Les Skills : apprendre un savoir-faire à Claude

La fonctionnalité la plus mal connue, et la plus utile sur la durée.

Une Skill est un dossier de consignes que Claude charge automatiquement quand le sujet s'y prête. C'est la mémoire méthodologique du projet : au lieu de réexpliquer vos exigences à chaque session, vous les écrivez une fois.

.claude/
└── skills/
    ├── design/
    │   └── SKILL.md          ← les consignes, en markdown
    ├── ui-ux-pro-max/
    │   ├── SKILL.md
    │   └── references/       ← documents consultés au besoin
    └── slides/
        └── SKILL.md

Chaque SKILL.md commence par un en-tête qui dit son nom et — surtout — quand l'utiliser :

---
name: slides
description: Créer des présentations HTML avec Chart.js, des tokens de
  design, des mises en page responsives. Utiliser quand l'utilisateur
  demande un diaporama ou une présentation.
---

# Consignes
1. Toujours partir des tokens de couleur du projet…

Les skills installées dans ce dépôt couvrent toutes le même besoin — obtenir des pages qui ne ressemblent pas à du HTML brut :

ui-ux-pro-max

Base de styles, palettes et associations de polices. C'est elle qui évite le « site des années 2000 ».

design / design-system

Identité visuelle, jetons de couleur et d'espacement, cohérence d'une page à l'autre.

slides

Diaporamas HTML avec graphiques, utilisables en vidéoprojection.

banner-design

Bandeaux et visuels d'en-tête aux bons formats.

brand

Ton, vocabulaire, règles de charte à respecter partout.

ui-styling

Composants d'interface accessibles : boutons, formulaires, tableaux.

Comment on s'en sert

  • Automatiquement : Claude lit les descriptions et charge celle qui correspond à la demande.
  • À la main : en tapant /nom-de-la-skill dans la conversation.
  • En créer une : /skill-creator, puis décrire la méthode à formaliser. Excellente idée pour un usage enseignant : une skill « fiche de révision maison » qui impose votre structure, votre vocabulaire et votre mise en page à chaque nouvelle fiche.

Piège rencontré sur ce dépôt

Un commit s'appelle Fix skill folder structure : les skills avaient été déposées au mauvais endroit et n'étaient donc jamais chargées. La structure exacte est impérative : .claude/skills/<nom>/SKILL.md, avec un en-tête name + description. Une skill mal rangée ne produit aucune erreur — elle est juste ignorée en silence.

10 Les serveurs MCP : brancher des outils extérieurs

Ce qui fait passer Claude du « dossier de fichiers » au reste du monde.

MCP (Model Context Protocol) est la prise standard qui permet à Claude de dialoguer avec un service extérieur. Une fois branché, le service devient un ensemble d'actions que Claude peut déclencher lui-même.

Le branchement se déclare dans le fichier .mcp.json, à la racine du projet :

{
  "mcpServers": {
    "21st": {
      "url": "https://21st.dev/api/mcp",
      "headers": { "x-api-key": "${TWENTY_FIRST_API_KEY}" }
    }
  }
}

Ici, le serveur 21st.dev donne accès à une bibliothèque de composants d'interface prêts à l'emploi. D'autres connecteurs s'activent côté compte, sans fichier à écrire :

ConnecteurCe que Claude peut alors faire
GitHubLire et créer des pull requests, commenter, consulter les tests automatiques
GmailChercher un fil, préparer un brouillon de réponse
CanvaCréer ou exporter un visuel à partir d'un modèle

Deux règles à énoncer

1. Un connecteur donne un accès réel à un compte réel : on n'active que ce dont on a besoin.
2. Le jeton d'accès ne s'écrit jamais en clair dans .mcp.json — d'où la notation ${TWENTY_FIRST_API_KEY}, expliquée juste en dessous.

11 Clés API et secrets : la partie à ne pas rater

Le seul chapitre où une erreur coûte de l'argent.

Une clé API est un mot de passe qui facture. Publiée sur GitHub, elle est repérée par des robots en quelques minutes et utilisée à vos frais. Le dispositif mis en place ici tient en trois fichiers :

FichierContenuPublié ?
.env.exampleTWENTY_FIRST_API_KEY= — le modèle, sans valeurOui, c'est une documentation
.envLa vraie cléNon, jamais
.gitignoreLa ligne .envOui — c'est elle qui interdit l'envoi du précédent

.gitignore est la liste des fichiers que Git doit ignorer. Tant que .env y figure, il est impossible de le publier par mégarde.

La solution retenue pour les pages publiques

Les outils du site qui appellent une IA (correction_copies.html, les chatbots) ne contiennent aucune clé. Au premier lancement, la page affiche un encadré : « Collez votre clé API Anthropic pour démarrer ». La clé reste dans le navigateur de la personne qui l'utilise. Chacun paie sa consommation, et la page reste publiable sans risque.

Si une clé a fuité

La supprimer du code ne suffit pas : elle reste dans l'historique Git. Il faut la révoquer sur le site du fournisseur et en générer une nouvelle. Toujours dans cet ordre.

12 Faire appeler l'IA par vos propres pages

La différence entre « Claude a écrit ma page » et « ma page utilise Claude ».

Deux choses distinctes, souvent confondues en formation :

Claude Code

L'assistant qui fabrique vos fichiers. Il n'est pas présent dans la page finale.

L'API Claude

Un service que votre page appelle pendant que l'élève s'en sert. C'est ce qui rend le chatbot capable de répondre.

Dans ce dépôt, trois pages appellent une IA en direct : correction_copies.html, rudy_ricciotti_chatbot.html et chatbot_svt_TERM_test.html. Le choix du modèle n'est pas anodin, et l'outil de correction laisse le correcteur décider :

ModèleProfilUsage typique dans le projet
claude-haiku-4-5Rapide et économiqueChatbot d'élève : beaucoup d'échanges courts
claude-sonnet-5ÉquilibréCorrection courante d'un paquet de copies
claude-opus-5Le plus finCopies délicates, barèmes très détaillés

Deux optimisations visibles dans la v9 méritent d'être citées, parce qu'elles s'appliquent à n'importe quel projet : le cache (ne pas repayer l'analyse d'un énoncé identique d'une copie à l'autre) et le choix du modèle selon la tâche (inutile de sortir le modèle le plus cher pour reformuler une consigne).

À dire pendant l'atelier

Vous n'avez pas besoin de comprendre le code de ces appels. Vous avez besoin de savoir qu'ils coûtent quelques centimes par usage, et que Claude Code sait vous chiffrer et optimiser cela si vous le lui demandez.

À cela s'ajoute le fichier CLAUDE.md : posé à la racine, il est lu au début de chaque session. Cela évite de répéter les mêmes consignes à chaque conversation.

14 Trois modes de travail à connaître

Utiles quand la demande dépasse la simple retouche.

Le mode plan

Claude analyse et propose une démarche sans modifier un seul fichier. On valide, on amende, et l'exécution ne démarre qu'ensuite. Le bon réflexe pour un gros chantier — la refonte d'un outil, par exemple.

Les agents

Pour une tâche large, Claude peut déléguer à des assistants spécialisés (exploration du code, revue, planification) qui travaillent en parallèle et lui rendent une synthèse.

Les tâches planifiées

On peut programmer un déclenchement automatique : « chaque lundi à 8 h, vérifie que tous les liens du site répondent et corrige ceux qui sont cassés ».

Les permissions

Claude demande votre accord avant les actions sensibles : envoyer sur GitHub, exécuter une commande, supprimer un fichier. On peut assouplir ces demandes pour des actions répétitives et sans risque (relire un fichier, lancer les tests). En formation, on garde les demandes d'autorisation actives : c'est justement ce qui rend visible ce que fait l'outil.
